## 4. 제품 기능 제안과 제약 검토 (d)

### 4-1. 위치 기반 "내 주변" 정렬 — **정적 사이트로 가능하나, 선행 조건 3개 (결정 필요)**
기술 방식: 사용자가 "내 주변" 버튼을 **눌렀을 때만** `navigator.geolocation.getCurrentPosition()` 호출 → 브라우저 안에서 하버사인 거리 계산 → 카드 순서만 재배열(`finder.js`의 sort와 같은 방식). 위치는 서버로 보내지 않고 저장하지 않으며 URL에도 넣지 않는다(공유 링크에 위치가 실리지 않게).
- **CSP**: `script-src 'self'`이므로 자체 호스팅 `/assets/js/near.js`는 통과 [측정: `default-src 'self'; script-src 'self'; connect-src 'none'`]. `connect-src 'none'`이라 코드가 실수해도 위치를 외부로 보낼 수 없다. 이는 개인정보 안내 근거로 쓸 수 있다.
- **선행 조건 ① 응답 헤더 충돌 [측정]**: 라이브 `permissions-policy: camera=(), microphone=(), geolocation=()`. 이 헤더가 **geolocation API를 완전히 막는다.** 헤더는 `build_site.py` 약 555행에서 생성. `geolocation=(self)`로 바꿔야 함 → AGENTS의 잠금 항목은 아니지만 보안 헤더 변경이므로 HANSET 운영 봇과 준태님 확인 필요. **결정 필요.**
- **선행 조건 ② 좌표 데이터 없음 [측정]**: `boxes.csv`/`saunas.csv`/`venues.json`에 위도·경도 필드가 없다(박스는 `address` 컬럼이 있으나 좌표가 아니고, 사우나는 주소 컬럼 없이 도시·구만 있음). 좌표는 사실 데이터이고 AGENTS상 프론트 PR이 사실을 바꿀 수 없으므로, **HANSET 운영 봇에 이슈로 `lat`/`lng` 필드 요청**(공식 페이지 기준 확인). 좌표 없이 쓰는 대안은 구 단위 중심점 표(정확도 낮음 [추정])이나 권장하지 않음.
- **선행 조건 ③ 고지**: 개인정보 페이지에 "위치는 이 기기에서만 계산하고 저장·전송하지 않아요" 한 줄 필요(현재 `privacy.html`에 '위치' 언급 0회 [측정]).
- **위치 거부/오류/시간 초과 폴백**: 사용자 메시지 한 줄 + 지역 칩(서울·부산·제주·경기)이 그대로 사용 가능. 지역 칩은 이미 존재(city 필터).
- **범위 한계 처리**: 업장이 31곳(서울 17)이라 서울·부산·제주·경기 외 지역은 가장 가까운 곳이 매우 멀 수 있음. "가장 가까운 곳 ○○km" 표기와 "근처(50km 안)에 등록된 곳이 없어요" 안내 필요 [추정].
- **[짐작]** 인스타그램 인앱 브라우저 등에서 geolocation 동작은 테스트하지 못함. 지역 칩 폴백이 1급 경로여야 하는 이유.
- 권장 단계: 1단계는 위치 없이 **지역·종류 칩만**, 위치 기능은 ①②③ 해결 후 3번째 PR.
